# Data format

Every problem is one YAML file at `data/problems/<folder>/<id>.yaml`.
The folder is determined by the entry's main idea (`key_idea.category`) through
`data/taxonomy.yaml`; `scripts/validate_entries.py` enforces this.

## Guiding question

Each entry must let a reader answer at once:

> **What is the one mathematical observation that changes how this problem
> should be viewed?**

That observation goes in `key_idea`. The `reasoning_structure` block then
records the contrast between the naive approach and the key idea.

## Schema

```yaml
id: mutilated_checkerboard          # snake_case; must equal the file name
title: Mutilated Checkerboard

aliases:                            # optional; other names the problem goes by
  - mutilated chessboard problem

source:                             # the canonical source of the entry
  name: Cut-the-Knot                # short, stable source name (see below)
  url: https://...                  # required; must be a URL
  original_title: ...               # title of the page / chapter / problem
  author: ...                       # optional
  accessed: 2026-09-16              # YYYY-MM-DD
  notes: ...                        # optional provenance notes (attribution, history)

additional_sources:                 # optional; same problem elsewhere
  - name: Wikipedia
    url: https://...
    original_title: ...
    notes: ...

problem:
  statement: >                      # concise statement in our own words
    ...
  domain: tiling                    # mathematical domain (free text, kept consistent)
  answer: impossible                # the answer / "proved" for prove-that problems

key_idea:
  name: checkerboard coloring       # a short name for the idea
  category: coloring_invariant      # an id from data/taxonomy.yaml
  summary: >                        # 1-3 sentences: the observation itself
    ...

intuitive_proof:
  explanation: >                    # a complete but short proof built on the key idea
    ...

reasoning_structure:
  naive_approach: >                 # what one would naturally try first
    ...
  crucial_observation: >            # what to notice instead
    ...
  why_it_simplifies: >              # why the observation collapses the problem
    ...

related:                            # optional; ids of related entries
  - gomory_opposite_colour_squares  # (also suppresses duplicate warnings for the pair)

tags:                               # required; at least two free-form tags
  - invariant
  - coloring

quality:                            # curation labels: low | medium | high
  clarity_of_key_idea: high
  elegance: high
  naive_search_contrast: high
  pedagogical_value: high

familiarity:                        # descriptive metadata only
  famous: true
  likely_widely_known: true

notes: ""                           # optional free text
```

### Required fields

`title`, `source.name`, `source.url`, `source.accessed`, `problem.statement`,
`problem.domain`, `problem.answer`, `key_idea.name`, `key_idea.category`,
`key_idea.summary`, `intuitive_proof.explanation`, all three
`reasoning_structure` fields, `tags`, `quality` (all four labels), and
`familiarity` (both booleans).

### Conventions

* Prose fields use YAML folded scalars (`>`); plain scalars must not contain
  `: ` (quote them if they do).
* Keep `problem.statement` under ~220 words and `intuitive_proof.explanation`
  under ~400 words; the validator warns otherwise.
* `source.name` values in use: `Cut-the-Knot`, `Wikipedia`,
  `Engel - Problem-Solving Strategies`, `Aigner & Ziegler - Proofs from THE BOOK`,
  `Fomin, Genkin, Itenberg - Mathematical Circles (Russian Experience)`,
  `Wolfram MathWorld`, `International Mathematical Olympiad <year>, Problem <n>`.
  Reuse these strings so that per-source counts stay meaningful.
* Do not copy source text. Statements and proofs are written in our own
  words; the URL is the pointer to the original.
* One canonical entry per problem. If a problem is known under several
  names, add `aliases` and `additional_sources` instead of a second file.

## Quality labels

| label | meaning |
|---|---|
| `clarity_of_key_idea` | can the idea be stated in one sentence and recognised as the whole point? |
| `elegance` | how short and surprising the intuitive proof is |
| `naive_search_contrast` | how much simpler the key idea is than the natural first attempt |
| `pedagogical_value` | how reusable the idea is for other problems |

These are curation judgements, not measurements.

## Index

`data/index.jsonl` is generated by `scripts/build_index.py` and holds one JSON
object per entry with identifying metadata, the key idea and its category
(leaf and root), source, tags, aliases, quality and familiarity. Long prose
fields are not included; read the YAML for those.
